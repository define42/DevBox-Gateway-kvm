# Disk performance evaluation — 2026-10-11

This evaluation compares gokvm before and after negotiated virtio-blk FLUSH
support and bounded QCOW2 refcount caching. It measures the disk path, not desktop
responsiveness, RDP encoding, or QEMU-relative performance.

## Changes

- Advertise `VIRTIO_BLK_F_FLUSH`. After the guest accepts it, ordinary writes may
  complete in the host page cache; explicit guest flushes synchronize the image
  before success is reported. Drivers that do not negotiate FLUSH retain the
  previous synchronous batch behavior.
- Preserve flush ordering and errors, retain dirty state across device reset,
  and wait for active I/O and synchronize dirty data before closing the image.
- Cache QCOW2 refcount blocks with a 4 MiB data budget. Metadata updates remain
  immediate; failed writes invalidate cached refcounts. This removes repeated
  refcount reads from allocated-cluster overwrites and image-open validation.

These semantics follow [Virtio 1.2, block device initialization and operation](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html).
Ordinary unflushed writes are volatile. Successful flushes are the durability
boundary; this is not an option to skip application-requested synchronization.

## Environment and method

- Intel Core i7-7700HQ, Linux/amd64, kernel `7.0.0-38-generic`, Go `1.26.8`.
- Samsung SSD 970 EVO Plus 1TB; ext4 on `/dev/nvme0n1p2`. Repository and `/tmp`
  reside on that filesystem. Benchmarks use newly created disposable disks.
- Guest: one vCPU, 256 MiB RAM, repository `bzImage`, a minimal initramfs, no
  desktop or network. The same Go workload runs on the host and in the guest.
- 64 MiB fully populated images, 64 KiB QCOW2 clusters, 4 KiB random operations,
  queue depth one. The overwrite benchmark excludes new-cluster allocation.
- Guest `O_DIRECT` bypasses the guest page cache. The gokvm backend still uses
  the host page cache. Warm guest reads are therefore not physical SSD reads.
  The report includes separate host-buffered and host-direct controls.
- Final guest comparisons use three rounds, two repetitions per round, and
  seeds 42–44. Order alternates before→after, after→before, before→after. Each
  repetition performs 512 operations per workload. No benchmark workloads run
  concurrently; this is a development workstation, not a dedicated lab host.

`random_write_sync1` includes a sync after every write. `random_write_sync32`
includes a sync after every group of 32 writes, including any final partial
group. Its IOPS and mean latency are amortized per write; its p99 includes the
sync-bearing operations and is not time-to-durability for every individual write.

The [harness guide](../../scripts/diskbench/README.md) documents reproduction,
settings, cache modes, and artifacts. Each completed invocation checks written
blocks, closes and reopens the images, runs `qemu-img check`, and compares every
logical byte across host, raw guest, and QCOW2 guest results. This checks data
consistency but does not simulate power loss.

## Guest results

Medians from six samples per target and workload:

| Disk / workload | Before IOPS | After IOPS | Before mean latency | After mean latency |
|---|---:|---:|---:|---:|
| Raw: sync every 32 writes | 277 | 4,400 | 3,613.9 µs | 227.3 µs |
| QCOW2: sync every 32 writes | 277 | 4,139 | 3,609.1 µs | 241.6 µs |
| Raw: sync every write | 272 | 248 | 3.679 ms | 4.035 ms |
| QCOW2: sync every write | 271 | 249 | 3.696 ms | 4.012 ms |
| Raw: warm random read | 11,464 | 10,794 | 87.23 µs | 92.65 µs |
| QCOW2: warm random read | 11,728 | 11,012 | 85.30 µs | 90.90 µs |

Grouped-write throughput improves **15.9× for raw** and **14.9× for QCOW2**.
The measured per-write-sync latency regression is **9.7% for raw** and **8.6% for
QCOW2**. A separate FLUSH request adds a guest/device round trip; this is a likely
contributor, not an isolated causal measurement. A workload that synchronizes
every individual write does not benefit from grouping. Both write changes are
statistically significant in these samples (`benchstat`, p ≤ 0.004, n = 6).

Read medians increased 6–7%, but that difference is not statistically significant
(p = 0.394 for each guest format). These samples do not establish a read-speed
improvement or rule out a smaller regression.

For context, host-buffered grouped writes remain about 7,980→7,937 IOPS, versus
4,400 raw-guest IOPS after the change. Host-direct grouped writes remain about
7,045→7,015 IOPS. Warm host-buffered reads are about 638,000→671,000 IOPS; host-direct
reads are about 14,600→14,400 IOPS. These different cache paths are not interchangeable
native-disk baselines. Host controls show no significant change except a 1.6%
increase in buffered per-write-sync latency. The guest disk path still has
substantial notification and scheduling overhead.

All six completed invocations passed write readback, QCOW2 metadata validation,
and byte-for-byte equality of the four logical disks after close/reopen. Workload
binaries and kernel were identical across versions; only the saved runtime
runner changed. Baseline runtime is commit `46a2dcfbc1f137355469377341ab5512fea7136a`.
An earlier exploratory run lacked the final reopen check after a harness edit;
none of its samples are included here.

## Backend microbenchmarks

These benchmarks run directly against the Go backend, without guest/KVM
notification overhead. There are ten samples per case, 500 ms minimum sample
time, taken sequentially before and after. The guest comparison controls host
drift more closely by alternating versions.

| Case | Before median | After median | Change |
|---|---:|---:|---:|
| Open allocated 64 MiB QCOW2 | 1,129.7 µs | 131.1 µs | −88.4% |
| Buffered QCOW2 4 KiB overwrite | 3.590 µs | 1.891 µs | −47.3% |
| QCOW2 4 KiB overwrite + sync | 3.138 ms | 3.253 ms | +3.7% |

The refcount cache helps metadata work and buffered overwrites. It does not
remove storage synchronization cost: the per-write-sync case was slightly slower
in this sequential microbenchmark. Open allocates about 64 KiB more for this
fixture's cached refcount block; steady-state reads and writes still allocate
zero Go heap objects per operation. The unmodified warm read path also measured
faster; that result is not attributed to the refcount-cache change.

A separate block-worker benchmark submits 32 writes individually and then
requires them to be durable. Writethrough takes a median **105.1 ms per group**
with 32 syncs; negotiated writeback takes **3.701 ms per group** with one sync.
This result excludes the Linux guest and KVM notification overhead.

## Validation

- Focused storage, block-device, and transport tests pass with the Go race detector.
- Full `go test -count=1 -timeout=5m ./...` passes inside the repository's isolated
  user/network namespace, including KVM boot tests. Running without that namespace
  first failed the existing TAP tests because the host user lacks `TUNSETIFF` permission.
- Full pinned `golangci-lint` reports zero issues; `gopls check` reports no
  diagnostics for the changed runtime files.
- Tests cover feature negotiation, unnegotiated fallback, flush ordering and
  retries, read-only disks, malformed descriptors, dirty reset/close behavior,
  concurrent close, refcount-cache eviction, metadata failures, and image growth.

The implementation still has one synchronous disk queue and worker. Multiqueue,
asynchronous host I/O, and `ioeventfd` remain separate optimization candidates;
none were needed to remove the measured per-write sync bottleneck.
